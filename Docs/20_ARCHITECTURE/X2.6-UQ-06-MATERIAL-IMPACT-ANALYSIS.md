## 2. Option A vs Option B — Impact Comparison

### 2.1 Option A — Standalone 将 Material / context 内化到 `stem / context`

> 单元级不保留独立 Material structure；语义上 material 并入 stem/context 文本。

| Dimension | Impact | Label |
|-----------|--------|-------|
| **Semantic correctness** | 对「配图/表格归属本题」的 standalone 可接受；**丢失** material 独立身份 / dedup / link | analysis on `DIRECTLY VERIFIED` surfaces |
| **Existing code compatibility** | **高** — 与当前 compiler/gate/`materials=()` 行为 **一致**；IR standalone 无 material role | `DIRECTLY VERIFIED` |
| **Schema impact** | **低** — `materials`/`material_links` 表可保留给 composite；standalone 不写 link | `DIRECTLY VERIFIED` |
| **Compiler impact** | **无** | `DIRECTLY VERIFIED` |
| **Gate impact** | **无**（`materials=()` 保持） | `DIRECTLY VERIFIED` |
| **Admission impact** | **低** — standalone 不建 material link | `DIRECTLY VERIFIED` |
| **Test impact** | **低** — 现有测试匹配现状 | `DIRECTLY VERIFIED` |
| **Historical data** | corpus standalone 用 stem/options/extra 承载配图 | `DOCUMENT-BACKED` |
| **Future extensibility** | **弱** — 后续 material 去重/引用/共享需回补结构 | analysis |
| **Implementation complexity** | **低** | analysis |
| **Risk** | 把「single q has no material」误写成系统全局事实（**禁止**）；丢失 Material 独立语义 | Owner invariant |

### 2.2 Option B — Standalone 保留独立 Material structure

> Unit 可挂 Material（与 composite 同构或子集）。

| Dimension | Impact | Label |
|-----------|--------|-------|
| **Semantic correctness** | **与 Papers 域模型一致**（standalone 可含配图/表格作为 material） | `DOCUMENT-BACKED` |
| **Existing code compatibility** | **低** — 与 compiler 仅-composite 产 material、gate `materials=()` **冲突**；须改多层 | `DIRECTLY VERIFIED` |
| **Schema impact** | **中低** — DB 表已存在且不按 unit_type 过滤；`UnitGroup.shared_material_id` 已 nullable 可用 | `DIRECTLY VERIFIED` |
| **Compiler impact** | **中** — 须允许 standalone 节点产 CompiledMaterial | analysis on code |
| **Gate impact** | **中** — `partition_candidate` else 分支、semantic checks、payload roles | `DIRECTLY VERIFIED` |
| **Admission impact** | **中** — standalone material link 路径 | analysis |
| **Test impact** | **中高** — gate/compiler/admission/policy 测试需扩展 | analysis |
| **Historical data** | historical standalone 配图是「已内化」还是「应回补 material」= `UNKNOWN` | `UNKNOWN` |
| **Future extensibility** | **强** — material dedup/link/figure pipeline 一致 | analysis |
| **Implementation complexity** | **中高** | analysis |
| **Risk** | 未裁 authority 前实施 = 擅自改 frozen domain 行为 | governance |

### 2.3 Comparison rollup

| Criterion | Option A（内化） | Option B（保留结构） |
|-----------|------------------|----------------------|
| Semantic（域模型对齐） | 部分 | **更好** |
| 与当前 V3 code | **一致** | 冲突（须改） |
| Schema | 低影响 | 中低（表已存在） |
| Complexity | **低** | 中高 |
| Extensibility | 弱 | **强** |
| 违反 Owner「不提前重构」风险 | 低（现状） | **若擅自实施则高** |

**Owner Decision 对照**:
- 「Standalone 在语义上 **可以** 将 Material 内化」→ A 在语义上 **被允许**
- 「若 architecture 已支持 Standalone→Material 且语义正确，**可以保留**」→ DB 层 **部分支持**；Compiler/Gate **未支持** standalone material
- 「先做 impact analysis，再决定」→ **本文件 = analysis 完成**；**决定 = Owner**
